# تسليم الإنتاج — تسجيل الفعلي من الشاشة القائمة

نسخة مصدر تجريبية **1.50.7-alpha.2** — `2026-09-09 ActualDeliveryDraft2`.
ليست حزمة تشغيل أو ترقية معتمدة. المرجع السابق 1.50.6 لم يُستبدل. نتائج التشغيل الفعلية وقيود القبول في حزمة الأدلة المصاحبة؛ Windows WPF غير منفذ في بيئة Linux.

## ما تغير

- الشاشة نفسها `ProductionDeliveryView` وبنفس رمزها MRPMPS1021؛ ليست شاشة جديدة.
- أوامر جميع خطط اليوم اليومية والفترية والعملاء والورديات تأتي من مرجع أمر اليوم المطابق للخطة المعتمدة. اختيار **أمر** عند تعدد الأوامر ليس اختيار صنف أو إنشاء خطة؛ يُختار الأمر المتاح الأول تلقائيًا.
- العميل والصنف والمخطط والوحدة ثابتة. لكل بند خانة **المنتج فعليًا بالكرتون**، والفرق يظهر مباشرة. لا إضافة/حذف أصناف تامة، ولا تغيير تاريخ أو كمية الخطة.
- خانة واحدة للعملية: **الخام المستهلك فعليًا — كجم**، تبدأ فارغة؛ وافق المستخدم عليها صراحةً. لا تُملأ من المخطط أو من وزن الإنتاج والمخلفات.
- ساعات توقف وسبب واحد للعملية، ومخلفات/مخرجات ثانوية مختارة وكمياتها بوحداتها، وملاحظات اختيارية.
- المصدر الثانوي هو قائمة المخرجات الموجودة في إعدادات المجموعات والفئات (`ByProducts`). لا أسماء ثابتة، ولا مساواة بين معرفاتها ومعرفات `Products` ذات المجموعة003؛ الكتالوجان مختلفان.
- حفظ واحد لتسجيل الفعلي وصرف الخام واستلام التام وإحالته إلى فحص معلق، ثم تُعرض أرقام المستندات ويحظر إعادة التسجيل.
- مدخلا الفعلي السابقان في تفاصيل الأمر يفتحان هذه الشاشة نفسها؛ أزيل نموذجَا الإقفال المنفصلان. التخطيط والبدء والجودة والاستلام التاريخي ليست محذوفة.
- الطباعة من التنفيذ المحفوظ؛ أضيف جدول المخطط/الفعلي/الفرق مع بقاء التوقفات والمخرجات السابقة وترتيبها. أضيف الفرق وسبب التوقف والخام والملاحظات إلى تقرير الإنتاج اليومي.

## الحفظ والترابط

`IProductionDeliveryService.SaveActualProduction` يعيد التحقق داخل معاملة SQL Server بدرجة SERIALIZABLE:

1. أمر مطابق تمامًا لخطة اليوم المعتمدة، بدأ تنفيذه، ولا يحمل تسجيلًا/فحصًا/استلامًا سابقًا.
2. معرفات جميع بنود الأمر نفسها مرة واحدة؛ طلب الحفظ لا يحتوي أصلًا حقولًا لاختيار العميل أو الصنف أو المخطط.
3. الفعلي عدد كراتين صحيح من صفر إلى المخطط لكل بند، وإجمالي إنتاج موجب؛ الوزن من وزن الكرتون الموروث في الخطة مع فحص اتساق الوحدة القائم.
4. خام صريح موجب، وأعداد محدودة صحيحة (لا NaN أو Infinity). توقف من صفر إلى24ساعة مع سبب عند وجوده. مخرج معرف نشط غير مكرر وكمية موجبة بدقة التخزين القائمة (4منازل).
5. استدعاء جوهر `ExecutionService.CloseProductionDay` القائم ثم `FinishedGoodsService.SaveReceipt → Issue → Receive`. الأطفال ينضمون صراحةً إلى المعاملة الأم؛ أي فشل يعيد **كل** التنفيذ والخام والمخزون والجودة والمخلفات والتوقفات.
6. تبقى حركة التام من سند الاستلام المخزني الموجود، لا كتابة رصيد موازية. العميل والدفعة والصنف والعبوة من الأمر، لا من المستخدم.
7. إعادة النقر أو الحفظ من جهازين لا تضاعف التسجيل. يعاد تنفيذ المعاملة كاملة عند تعارض SQL deadlock، لا جزء منها.

### الخام والزيادة بالماء

الحقل يعني **صافي الخام المستهلك فعليًا**. لذلك لا يعاد خام تلقائيًا إلى المخزون لمجرد أن مجموع الخارج أقل من هذا الرقم. عند تعدد دفعات الخام يُوزع الإجمالي المدخل بنسب بنود الأمر وفق الدورة القائمة، مع حفظ الإجمالي دون فقد بالتقريب. هذا **توزيع للإجمالي المقاس** وليس استنتاجًا له. الواجهة توضّح ذلك. لا يوجد هنا إدخال استهلاك مستقل لكل دفعة.

زيادة وزن الخارج عن الخام بسبب ماء التشغيل لا تُرفض. المخرج ذو وحدة غير وزنية يسجل بوحدته ولا يعامل في حساب التنفيذ على أنه كيلوجرام.

### الجودة والصلاحيات

الإحالة الفورية لا تعني الفحص أو الاعتماد. المحضر **مرسل للفحص وغير معتمد**. بنوده تحمل هوية الأصناف والدفعات، لكن الكميات المفحوصة والمقبولة فيها صفر حتى تدخل النتيجة الفعلية. كميات الإحالة تظهر في مرجع التنفيذ وملاحظات البنود، وإجماليات الإحالة في الرأس وفق الدورة القائمة. لا يجوز استخدام تلك البنود كدليل فحص مكتمل.

سند المخزون معتمد بوصفه **استلامًا مخزنيًا** لا اعتماد جودة. بوابة تسليم العميل تبقى مغلقة حتى إدخال واعتماد نتيجة الجودة رسميًا. يستكمل الفحص المعلق نفسه، ولا ينشأ فحص مكرر.

لا يوجد تجاوز صلاحيات: الحفظ يتطلب `production/Create` و`execution/Edit` و`finishedgoods/Create` و`finishedgoods/Approve`. لم تُمنح أدوار الإنتاج صلاحية مخزن ضمنيًا. يجب ضبط الدور المخول بهذه العملية وفق سياسة المنشأة قبل التشغيل. لا تُنفذ فاتورة أو بيع أو قيد حسابي من الشاشة.

## حالة الاختبار الإلزامية

- سكري، وزن كرتونه التعريفي8كجم: مخطط3000كرتون، فعلي2700، فرق300.
- توقف1ساعة، السبب «عطل ماكينة»، مخرج معرف اختباري مختار200كجم.
- الخام **22000كجم قيمة اختبار مدخلة صراحةً**؛ ليست معلومة افترضناها من المستخدم.
- المخطط يظل3000/24000كجم، الفعلي2700/21600كجم؛ الخام يصرف22000بالضبط؛ سند التام يورد2700كرتون لنفس العميل والدفعة؛ إحالة الجودة معلقة.
- اختبارات إضافية: قيم خاطئة/أجنبية/مكررة، مخرج موقوف، فشل متأخر بعد كتابة التنفيذ داخل المعاملة، ضغطتان، جهازان على SQL Server، صنفان مع توقف واحد، نفس الصنف من دفعتين، عميل ثانٍ، زيادة وزن بالماء، ثم استكمال واعتماد الجودة بصورة منفصلة.
- الفرق مشتق من المخطط والفعلي المحفوظين؛ ليس عمودًا ثالثًا قابلًا لعدم التزامن.

## حدود واضحة لا تُخفى

- Windows WPF لم يُشغّل هنا. مشروع `tools/ActualDeliveryWpfSmoke` فحص نافذة WPF الحقيقية والأحداث والحفظ إلى قاعدة معزولة، **مبني فقط** ولا يُعد نجاحه في البناء قبولًا بصريًا.
- لا قبول على نسخة قاعدة بيانات المستخدم، ولا ترقية تلقائية للسجلات السابقة. أمر فيه تنفيذ/فحص/سند سابق لا يعاد ترحيله تلقائيًا من الشاشة الجديدة، حماية من الازدواج. تبقى مستنداته وخدماته وتقاريره القديمة.
- تسجيل أقل من المخطط لا يخفض الخطة ولا يسوي الباقي إداريًا. حالات إغلاق الخطة/الأمر تتبع الدورة القائمة؛ لا تخطيط تلقائي لبقية300كرتون.
- لا تسجيل يوم بلا إنتاج تام قابل للتسليم في هذه العملية، ولا سجل دفعات إنتاج متكرر لنفس الأمر.
- المخلفات هنا تسجل في سجلات التنفيذ وتقاريره؛ لا ادعاء بتوريدها إلى رصيد أصناف `Products`، فهذه ليست هويات القائمة نفسها.
- نتائج الاختبارات الشاملة المتبقية عائق إصدار، وليست معفاة باعتبارها قديمة.

## إعادة التنفيذ

```bash
dotnet build DateERP.sln -c Release -m:1 -nodeReuse:false -p:UseSharedCompilation=false -warnaserror
dotnet test tests/DatesErp.Tests -c Release --no-build
dotnet run --project tools/PlanningAcceptance -c Release -- --actual-delivery
# DATEERP_TEST_SQL يضبط خارجيًا دون وضع كلمة مرور في ملف المصدر:
dotnet run --project tools/PlanningAcceptance -c Release -- --actual-delivery --sql
```

يمكن ضبط `DATEERP_ACCEPTANCE_JSON` لخطوات القبول و`DATEERP_ACTUAL_EVIDENCE_JSON` للقطة مقروءة من قاعدة البيانات عند **مرحلة انتظار الجودة قبل اعتمادها**. ينشئ اختبار SQL قاعدة GUID معزولة ويحذفها وحدها بعد الاختبار.

على Windows مع .NET8 وSQL Server اختبار:

```powershell
dotnet run --project tools/ActualDeliveryWpfSmoke -c Release -- --sql
```

الاختبار يفتح الشاشة الحقيقية، يدخل2700في محرر الجدول، ويختار مخرجًا منComboBox، ويدخل200والخام22000والتوقف1والسبب، ثم ينقر زر الحفظ ويفحص المخزون والجودة وإغلاق التحرير. يلزم أيضًا قبول يدوي على صلاحيات المستخدم الفعلية وبيانات ممثلة قبل التشغيل.
