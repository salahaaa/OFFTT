# أمر إنتاج اليوم — مسودة 1.50.7-alpha.1

**ختم البناء:** `2026-09-09 TodayOrdersDraft1`.

> هذه مسودة تطوير وليست تحديث إنتاج معتمداً. نجح سيناريو القبول الجديد على SQL Server، لكن فحص الانحدار الشامل لم يصبح أخضر بعد، ولم تُشغّل واجهة WPF على Windows في هذه البيئة. لا تستبدل بها النسخة التشغيلية.

## القاعدة المتفق عليها

أمر الإنتاج لا يخطط ولا يقترح ولا يضيف أصنافاً، ولا يغير كمية الخطة. مصدره فقط **البنود المجدولة لليوم من الخطط المعتمدة**.

وفق إجابات المستخدم:

- تشمل الشاشة كل الخطط اليومية والفترية المعتمدة التي تحتوي بنوداً لليوم.
- تشمل كل العملاء والورديات تلقائياً دون اختيار خطة أو إعادة اختيار أصناف.
- تُوقف مسارات إصدار الأوامر المنافسة فقط؛ تبقى شاشات التخطيط والتنفيذ الفعلي والجودة والمخزون اللازمة للدورة.

## ما يظهر

الشاشة الموجودة `OrdersView` أصبحت «أمر إنتاج اليوم». تعرض العميل والصنف وكمية اليوم والوحدة والوردية والخط ومرجع الخطة والأمر وحالة التنفيذ. الصفوف للقراءة فقط؛ لا قوائم أصناف عامة ولا حقول لتغيير التاريخ أو الكمية ولا إضافة/حذف بنود.

كل صف يحتفظ بعميله ومرجع بند الخطة؛ لا تُجمع ملكيات عملاء مختلفين في سطر يفقد التتبع. الإصدار يولد أمراً لكل **خطة × عميل × وردية × خط**، داخل معاملة واحدة لكل اليوم. التجميع داخلي لا يحتاج لاختيار العامل.

فتح الشاشة لا يحفظ أوامر ولا يصرف مخزوناً. زر «إصدار أوامر اليوم من الخطة» ينقل جميع البنود التي لم تصدر أوامرها، وبنفس الكميات. فتح الشاشة مرة أخرى أو تكرار الإصدار لا ينشئ نسخاً مكررة. بعد الإصدار تبقى كمية الخطة الأصلية ظاهرة ولا تصبح «صفر متبقٍ» بدلاً منها.

عند عدم وجود بنود معتمدة لليوم تظهر:

**لا توجد بنود إنتاج معتمدة ومجدولة لليوم. راجع جهة التخطيط؛ لا يمكن إنشاء أمر إنتاج.**

اليوم يُقرأ من `Db.BusinessNow`، أي وقت SQL Server المشترك، وليس تاريخ يرسله المستخدم. يجب ضبط توقيت خادم التشغيل على توقيت المنشأة. في اختبارات SQLite يُستخدم `TimeProvider` قابل للضبط للاختبار. لا يوجد تاريخ 9/9/2026 ثابت في منطق التشغيل.

لا ينقل النظام بند أمس أو غد إلى اليوم، ولا يخمن تاريخاً لبند فترة بلا جدولة. تظل السجلات القديمة محفوظة في قاعدة البيانات والتقارير؛ لا تُحذف بسبب إخفائها من شاشة اليوم.

## الحماية في الخلفية

- `GetTodayProduction()` يستخرج الصفوف من `ProductionPlanItems` المرتبطة بخطط معتمدة؛ أسماء Master مجرد أسماء لمعرفات تلك الصفوف، وليست مصدر قائمة الاختيار.
- `IssueTodayOrders()` لا يستقبل أصنافاً أو كميات أو تاريخاً من الواجهة. يعيد القراءة من القاعدة وقت الإصدار.
- واجهة `SaveOrder` القديمة باقية للتوافق البرمجي فقط مع فحص صارم: خطة معتمدة، يوم الخادم الحالي، مراجع البنود كاملة وفريدة، المجموعة كاملة، هوية العميل/الصنف/الدفعة/العبوة، وتساوي الكراتين والكيلو مع الخطة. الأمر اليدوي مرفوض حتى لو كان المستدعي مدير النظام.
- `UpdateOrderItems` و`UpdateOrderHeader` يرفضان التعديل؛ لا تغيير لكمية الأمر أو هويته أو تاريخ تنفيذه من هذه المسارات.
- الاعتماد وبدء التنفيذ والاستئناف يعيدون مطابقة الأمر مع خطة اليوم المعتمدة؛ لا تكفي شاشة للقراءة فقط.
- المعاملة `Serializable` تحمي من إصدار نفس بند الخطة من جهازين؛ فشل مجموعة لا يترك مجموعات اليوم محفوظة جزئياً.
- أمر سابق جزئي أو مخالف لا يُستكمل أو يُستبدل بصمت. تظهر حالة تعارض ويُمنع الإصدار حتى المراجعة الرسمية. لا يفتح رابط التفاصيل أمراً يحتوي بنداً إضافياً مخالفاً.
- لا يسمح مسار تعديل تقدم الخطة بتغيير بند مرتبط بأمر صادر، حتى لا ينفصل الأصل المعتمد عن أمر التنفيذ.
- فحص الطاقة يعيد استخدام حساب الخطة المشترك، دون إضافة طاقة مستقلة لكل أمر. الخطة القديمة التي لم تحدد وردية/خطاً تبقى كذلك؛ لا تُعيّن أول وردية تلقائياً.

## المسارات الموقوفة وما بقي

أزيلت واجهات `NewOrderPanel` و`IssuePlanWindow` و`DayRunWindow` ومداخلها. خدمة `DayRunService` و`IssueOrdersFromPlan` القديمة ترفض الإصدار وتوجه إلى مسار اليوم، فلا يكفي استدعاؤها بعيداً عن الواجهة للتحايل.

لم تُنشأ شاشة إنتاج جديدة؛ أعيد استخدام شاشة الأوامر وتفاصيل التنفيذ الموجودة. بقيت أزرار التنفيذ ذات المعنى: اعتماد المواد، بدء الإنتاج، التوقف والاستئناف، تسجيل الفعلي والإقفال، والطباعة حسب الحالة والصلاحية.

**كمية الأمر ليست الإنتاج الفعلي:** إذا كانت الخطة 3000 والأمر 3000 ثم أُنتج فعلياً 2700، يُسجل الفعلي 2700 دون تحويل كمية الأمر إلى 2700. تسوية العجز تتبع دورة الإقفال القائمة. لا تُفرض معادلة مساواة وزن الخام بالمنتج؛ قاعدة زيادة الوزن بماء التشغيل محفوظة.

## الاختبارات القابلة لإعادة التنفيذ

من جذر المصدر مع .NET SDK 8:

```powershell
dotnet build DateERP.sln -c Release -warnaserror
dotnet test tests/DatesErp.Tests -c Release --filter "FullyQualifiedName~TodayOrders"
dotnet run --project tools/PlanningAcceptance -c Release -- --orders
```

قبول الخدمات على **خادم SQL Server للاختبار فقط**، بصلاحية إنشاء وحذف قاعدة اختبار:

```powershell
$env:DATEERP_TEST_SQL = 'Server=.\SQLEXPRESS;Integrated Security=true;Encrypt=true;TrustServerCertificate=true;Connect Timeout=30;'
dotnet run --project tools/PlanningAcceptance -c Release -- --orders --sql
```

المثال يستخدم شهادة اختبار محلية؛ اضبط شهادة موثوقة في التشغيل. لا تضع كلمة مرور في ملفات المصدر أو ترسلها في المحادثة. تنشئ الأداة قاعدة عشوائية خاصة بها وتحذف تلك القاعدة فقط. لا تستخدم قاعدة التطبيق المكونة في إعداداته.

### قبول WPF الفعلي المتبقي

على **Windows** مع .NET SDK 8 وخادم SQL Server للاختبار:

```powershell
$env:DATEERP_TEST_SQL = 'Server=.\SQLEXPRESS;Integrated Security=true;Encrypt=true;TrustServerCertificate=true;Connect Timeout=30;'
dotnet run --project tools/TodayOrdersWpfSmoke -c Release -- --sql
```

هذه الأداة بُنيت فقط هنا ولم تُشغّل. تفتح شاشة `OrdersView` الحقيقية بمواردها وDataGrid الفعلي، على قاعدة `DateERP_TodayWpf_<GUID>` معزولة. تنشئ صنفي المثال وصنفاً ثالثاً وخطط أمس/اليوم/غد، وتختبر الفتح قبل الاعتماد وبعده، ورفض تحرير الخلايا وإضافة الصفوف، ثم تضغط زر الإصدار الحقيقي وتراجع قاعدة البيانات. تمنع نقطة اختبار الواجهة فتح تفاصيل تستخدم إعدادات قاعدة التشغيل.

تشغيل الأداة دون `--sql` يستخدم SQLite؛ لا يعادل قبول Windows مع SQL Server. يلزم أيضاً فحص بصري بشري على بيانات اختبار، يشمل تعدد العملاء والورديات والتنقل إلى تنفيذ الأمر. لا توجد صور Windows ملفقة ضمن الأدلة.

## حدود التسليم وموانع الاعتماد

1. فحص الانحدار الشامل ما زال يتضمن إخفاقات؛ ليس مسموحاً افتراض أن كل إخفاق قديم مجرد اختلاف توقع دون مراجعته. بعض تجهيزات اختبارات الجودة والمخزون حُولت إلى إصدار من خطة اليوم، وبقيت حالات أخرى للمراجعة.
2. اختبار WPF الحقيقي على Windows والفحص البصري لم يُنفذا هنا.
3. يلزم اختبار نسخة معزولة من قاعدة المستخدم، خصوصاً الأوامر اليدوية والجزئية السابقة، قبل التفكير في الترقية. لا يوجد في هذه المسودة ترحيل تلقائي أو حذف أو إعادة كتابة لهذه السجلات.
4. لم يُبن إجراء جديد لتعديل الخطة بعد إصدار أمرها. أي طلب تعديل يتطلب مساراً رسمياً يحفظ تاريخ الاعتماد والتنفيذ؛ لا يُحل بتعديل كمية الأمر.
5. لا تُقدَّم هذه المسودة كحزمة نشر إنتاجي، ولا تُلغى الإخفاقات ولا تُخفى لتحويل الفحص إلى نتيجة خضراء.
